ตรวจจากไฟล์ `001_init_schema.sql` และ `SCHEMA_DESIGN.md` ที่แนบมา เทียบทีละบรรทัด พบปัญหาทั้งหมด **19 จุด** แบ่งเป็น 4 ระดับความรุนแรง ทุกจุดแก้ไขแล้วในไฟล์ `001_init_schema_v2.sql` ที่แนบมาด้วย (ใช้แทนไฟล์เดิมได้เลย โครงสร้างและลำดับ section เหมือนเดิม แค่แก้จุดที่ระบุ พร้อมคอมเมนต์กำกับ `[แก้ไข]` / `[ใหม่]` ไว้ในโค้ดทุกจุด)

> สมมติฐานที่ยืนยันกับคุณแล้ว: นักเรียน/ครู/แอดมิน **ทุกคนมีบัญชี Supabase Auth จริง** — สคริปต์ v2 อิงตามนี้ทั้งหมด

## 🔴 ระดับวิกฤต — ทำให้สคริปต์รันไม่ผ่าน หรือรันผ่านแต่พังตอนใช้งานจริง

### 1. `CREATE INDEX` อ้างคอลัมน์ที่ไม่มีอยู่จริง (สคริปต์รันไม่ผ่านตั้งแต่บรรทัดนี้)
```sql
CREATE INDEX idx_borrow_book   ON public.borrow_records(book_id);
CREATE INDEX idx_borrow_active ON public.borrow_records(book_id, returned_at) ...
```
ตาราง `borrow_records` ไม่มีคอลัมน์ `book_id` (มีแต่ `book_copy_id` ตามดีไซน์เล่มลูก) — Postgres จะโยน error `column "book_id" does not exist` ทันที และสคริปต์ทั้งไฟล์จะหยุดตรงนี้ (ทุกอย่างหลังจากนี้ไม่ถูกสร้าง รวมถึง Policy และ Seed data)
**แก้แล้ว**: เปลี่ยนเป็น `book_copy_id` ทั้งสอง index (ดูหมวด 8 ในไฟล์ v2)

### 2. `users.id` DEFAULT + FK เขียนขัดกันเอง จนพังตอนลบ auth user
```sql
id UUID PRIMARY KEY DEFAULT auth.uid() REFERENCES auth.users(id) ON DELETE SET NULL
```
สองปัญหาซ้อนกัน:
- `id` เป็น **PRIMARY KEY** ซึ่งบังคับ `NOT NULL` เสมอ แต่ตั้ง `ON DELETE SET NULL` ไว้ — พอมีการลบ auth user ที่มีโปรไฟล์ห้องสมุดอยู่ Postgres จะพยายามเซ็ต `id = NULL` แล้วชนกับ PK constraint ทันที เกิด error กลางอากาศ
- `DEFAULT auth.uid()` อันตรายกว่านั้น — ถ้าแอดมินเป็นคนกด "เพิ่มนักเรียนใหม่" (เจ้าหน้าที่ล็อกอินอยู่ ไม่ใช่นักเรียน) แล้วโค้ดฝั่ง client ลืมส่ง `id` มาชัดเจน ระบบจะเผลอเอา `auth.uid()` ของ **แอดมินเอง** ไปตั้งเป็น id ของนักเรียนคนนั้น กลายเป็นสร้างโปรไฟล์ผิดคน แล้วพอสร้างคนที่ 2 จะชนกันทันทีเพราะ id (PK) ซ้ำ

**แก้แล้ว**: ลบ `DEFAULT auth.uid()` ออก (บังคับให้ต้องส่ง id มาเสมอ) และเปลี่ยนเป็น `ON DELETE CASCADE` แทน — เนื่องจากยืนยันแล้วว่าทุกคนมีบัญชี auth จริง การลบบัญชี auth ควรหมายถึงลบโปรไฟล์ห้องสมุดไปด้วย พร้อมเพิ่ม **trigger อัตโนมัติ** `handle_new_auth_user` บน `auth.users` ให้สร้างโปรไฟล์ `public.users` ทันทีที่มีคนสมัคร (อ่านค่า `user_id_code`, `full_name`, `role` จาก metadata ตอน signUp) — ตัดปัญหาการลืมสร้างโปรไฟล์ หรือสร้างผิดคนไปเลย

### 3. Seed data ของ `users` จะ INSERT ไม่ผ่าน (FK ชี้ auth.users ที่ไม่มีอยู่จริง)
```sql
INSERT INTO public.users (id, ...) VALUES ('11111111-1111-1111-1111-111111111111', ...)
```
UUID ที่ตั้งเองพวกนี้ไม่มีแถวคู่กันใน `auth.users` เลย ถ้า `users.id` ยังมี FK ไปยัง `auth.users(id)` (ซึ่งควรมีอยู่แล้วตามดีไซน์) INSERT นี้จะถูกปฏิเสธด้วย FK violation
**แก้แล้ว**: ห่อ seed ของ users ด้วย `SET session_replication_role = replica;` ... `SET session_replication_role = DEFAULT;` เพื่อปิดการเช็ค FK/trigger ชั่วคราว **เฉพาะตอน seed ข้อมูลทดสอบใน dev เท่านั้น** — มีคอมเมนต์เตือนชัดเจนในไฟล์ว่าห้ามใช้เทคนิคนี้กับ production และบอกวิธีที่ถูกต้อง (สร้างผ่าน Supabase Auth ก่อน แล้ว trigger ข้อ 2 จะสร้างโปรไฟล์ให้เอง)

### 4. `book_copies` และ `fine_payments` ไม่ได้เปิด RLS เลย (ช่องโหว่ความปลอดภัยที่ร้ายแรงที่สุดในไฟล์)
Section 12 ของไฟล์เดิมเปิด RLS ให้ 5 ตาราง แต่ตกหล่น 2 ตารางนี้ไป — เท่ากับว่าใครก็ตามที่ถือ `anon` key (กุญแจสาธารณะที่ฝังในเว็บได้เลย) จะ **อ่าน/เขียนได้ไม่จำกัด** โดยเฉพาะ `fine_payments` ที่เก็บ `slip_image_url` และยอดเงินของนักเรียนทุกคน ถือเป็นข้อมูลส่วนตัวที่รั่วไหลได้ทันที
**แก้แล้ว**: เพิ่ม `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` ให้ทั้งสองตาราง พร้อม Policy ชุดใหม่ (`book_copies`: public เห็นได้/แก้ได้เฉพาะ admin เหมือน `books`, `fine_payments`: เจ้าของหรือ admin เท่านั้นที่เห็น, insert ได้เฉพาะเจ้าของ/admin, update (อนุมัติ/ปฏิเสธ) ได้เฉพาะ admin, ไม่เปิด delete policy เลยเพื่อรักษา audit trail)

## 🟡 ระดับสูง — ข้อมูลไม่ตรงกันหรือหายได้โดยไม่ตั้งใจ (ไม่ทำให้ error แต่อันตรายต่อข้อมูล)

### 5. Seed หนังสือใส่ `total_copies`/`available_copies` มือ แต่ไม่เคยสร้าง `book_copies` จริง
เอกสารดีไซน์ระบุชัดว่าตัวเลขสองคอลัมน์นี้ "คำนวณอัตโนมัติจาก `book_copies` (Trigger)" แต่ seed data เดิม INSERT ตัวเลข (3, 2, 2, 4, 2, 1, 2 เล่ม) ตรงๆ โดยไม่เคยสร้างแถวใน `book_copies` เลยสักแถว — พอมีใครไปแก้ไข `book_copies` ของหนังสือเล่มไหนในอนาคต ตัวเลขจะถูก trigger คำนวณใหม่เป็น 0 ทันที (เพราะไม่มี book_copies จริงอยู่)
**แก้แล้ว**: เพิ่ม seed `book_copies` จริง (สร้าง barcode ให้ครบตามจำนวนเล่มเดิม เช่น `BK-M4-001-C1`, `BK-M4-001-C2`, `BK-M4-001-C3`) แล้วปล่อยให้ trigger คำนวณ `total_copies`/`available_copies` เองอัตโนมัติ — ตอนนี้ตัวเลขในตาราง `books` จะตรงกับข้อมูลจริงเสมอ

### 6. `ON DELETE CASCADE` บนตารางประวัติ ทำให้ audit trail หายได้ทั้งพวง
จุดที่เดิมตั้ง CASCADE ไว้ (แล้วเปลี่ยนเป็น RESTRICT ใน v2):
| ตาราง.คอลัมน์ | เดิม | แก้เป็น | เหตุผล |
|---|---|---|---|
| `book_copies.book_id` | CASCADE | RESTRICT | ลบหนังสือ 1 เล่ม ไม่ควรพาเล่มลูก + ประวัติการยืมทั้งหมดของเล่มนั้นหายไปด้วย |
| `borrow_records.user_id` | CASCADE | RESTRICT | ลบนักเรียน ไม่ควรพาประวัติการยืม/ค่าปรับของเขาหายไปด้วย |
| `borrow_records.book_copy_id` | CASCADE | RESTRICT | เหตุผลเดียวกับข้อบน |
| `fine_payments.borrow_record_id` | CASCADE | RESTRICT | ข้อมูลการเงิน ต้องเก็บ audit trail ไว้เสมอ |
| `fine_payments.user_id` | CASCADE | RESTRICT | เหตุผลเดียวกับข้อบน |

ผลคือตอนนี้ถ้าใครมีประวัติยืม/ค่าปรับค้างอยู่ ระบบจะ **บล็อกการลบ** โดยอัตโนมัติที่ระดับฐานข้อมูล บังคับให้ใช้ `status='suspended'` (สำหรับ users) หรือ `status='removed'` (สำหรับ books) แทนการลบจริงเสมอ — ส่วน `room_access_logs.user_id` ปล่อยเป็น `SET NULL` ตามเดิมได้ เพราะเป็นแค่สถิติ ไม่ใช่ข้อมูลการเงิน/สิทธิ์ ลบ user แล้วเก็บ log ไว้แบบไม่ระบุตัวตนก็ยังมีประโยชน์กับรายงานรายวัน

### 7. แจ้งหนังสือ "สูญหาย" แล้ว book_copies ไม่ถูกอัปเดตสถานะ
ใน `trg_borrow_update_copy_status()` เดิม มีแค่ 2 เงื่อนไข (ตอนยืม กับ ตอนคืน) — ถ้าเจ้าหน้าที่เปลี่ยน `borrow_records.status` เป็น `'lost'` โดยไม่ได้ set `returned_at` เล่มลูกใน `book_copies` จะค้างสถานะ `'borrowed'` ตลอดไป ไม่มีวันถูกทำเครื่องหมายว่าสูญหายจริง ทำให้รายงานสต็อกไม่ตรงความจริง
**แก้แล้ว**: เพิ่มเงื่อนไขใน trigger ให้ sync `book_copies.status = 'lost'` ทันทีที่ `borrow_records.status` เปลี่ยนเป็น `'lost'`

## 🟢 ระดับ Performance — ตรงตามที่ขอ "ลดการ query ที่ไม่จำเป็น"

### 8. `book_copies` ไม่มี index เลยสักตัว
Trigger `trg_sync_book_counts` ยิง `SELECT COUNT(*) FROM book_copies WHERE book_id = ... [AND status='available']` ทุกครั้งที่มีการเพิ่ม/แก้ไข/ลบเล่มลูกแม้แค่ 1 เล่ม — พอคลังหนังสือโตขึ้นจะกลายเป็น full table scan ทุกครั้ง
**เพิ่มแล้ว**: `idx_book_copies_book_status ON book_copies(book_id, status)`

### 9. ไม่มี index รองรับ query แพทเทิร์นที่ใช้บ่อยที่สุดของระบบ
เพิ่ม index ใหม่ 5 ตัว:
- `idx_borrow_user_status` — หน้า "ประวัติการยืมของฉัน" กรอง user_id + status พร้อมกันเสมอ
- `idx_borrow_overdue_check` (partial index เฉพาะแถวที่ยังไม่คืน) — ใช้กับ `mark_overdue_books()` ที่รันทุกเที่ยงคืน และหน้ารายงาน "เกินกำหนดคืน" ไม่ต้องสแกนทั้งตาราง
- `idx_borrow_handled_by` — หน้า "รายการที่ฉันทำ" ของเจ้าหน้าที่
- `idx_fine_payments_user_status` — `trg_sync_fine_balance` ยิง `SUM(amount) WHERE user_id=... AND status='approved'` ทุกครั้งที่มีการอนุมัติ/ปฏิเสธการจ่ายเงิน ไม่มี index ตัวนี้จะช้ามากเมื่อมีประวัติการจ่ายเยอะขึ้น
- `idx_access_checkin_date` (expression index บน `check_in_at::date`) — รองรับ query "สถิติเข้าใช้งานรายวัน" ที่ทำ `GROUP BY DATE(check_in_at)` โดยตรง

### 10. Dashboard ต้องยิงหลาย query แยกกันทั้งที่รวมเป็นคำสั่งเดียวได้
หน้า Dashboard (`/`) ตามสเปกต้องโชว์ 4 ค่าพร้อมกัน: คนอยู่ในห้องตอนนี้, ยืมวันนี้กี่เล่ม, เกินกำหนดกี่รายการ, ค่าปรับค้างชำระรวมเท่าไหร่ — ถ้าทำแบบเดิม (query ทีละตาราง) จะเป็น 4 round-trip ต่อการโหลดหน้าเดียว
**เพิ่มแล้ว**: ฟังก์ชัน `get_dashboard_stats()` รวมทั้ง 4 ค่าไว้ใน query เดียว (จำกัดสิทธิ์เฉพาะ admin) เรียกจาก frontend ครั้งเดียวจบ

### 11. ไม่มี view รวม join ที่ frontend ต้องใช้ซ้ำๆ
หน้า "รายการยืม-คืน" (`/borrow`, `/return`, `/history`) ต้อง join `borrow_records` + `book_copies` + `books` + `users` ทุกครั้งที่แสดงผล ถ้าทำ join นี้จาก client (เรียกทีละตาราง) จะกลายเป็นหลาย query ต่อ 1 หน้าจอ
**เพิ่มแล้ว**: 4 views สำเร็จรูป —
- `v_active_borrows` (รายการกำลังยืมอยู่ join ครบทุกตาราง)
- `v_overdue_borrows` (กรองต่อเฉพาะเกินกำหนด)
- `v_currently_in_room` (คนอยู่ในห้องตอนนี้ + ชื่อ)
- `v_popular_books` (หนังสือยอดนิยม เรียงตามจำนวนครั้งที่ถูกยืม)

ทุก view ยังคงเคารพ RLS ของตารางต้นทางตามปกติ (สมาชิกทั่วไป query `v_active_borrows` จะเห็นแค่แถวของตัวเอง เพราะ policy ของ `borrow_records` จำกัดไว้อยู่แล้ว)

### 12. `updated_at` ของ `book_copies`/`fine_payments` ไม่เคยถูกอัปเดตอัตโนมัติ
สองตารางนี้มีคอลัมน์ `updated_at` แต่ไม่มี trigger ใดแตะมันเลยนอกจากตอน INSERT ครั้งแรก — ค่าจะค้างเป็นเวลาสร้างแถวตลอดไป ทั้งที่ตั้งใจให้ track "แก้ไขล่าสุดเมื่อไหร่" (เช่น เปลี่ยนสภาพหนังสือ, เปลี่ยนสถานะการจ่ายเงิน)
**แก้แล้ว**: เพิ่มฟังก์ชันกลาง `set_updated_at()` + ติด `BEFORE UPDATE` trigger ให้ทั้งสองตาราง

## 📝 ระดับเอกสาร — SCHEMA_DESIGN.md กับโค้ดจริงไม่ตรงกัน

### 13. Mermaid ERD ที่หัวเอกสารเป็นเวอร์ชันเก่า
ตาราง `USERS` ใน ERD ใช้ชื่อคอลัมน์ `student_id`, `room`, role `student/teacher/admin` — แต่ตารางจริง (และตารางรายละเอียดถัดมาในไฟล์เดียวกัน) ใช้ `user_id_code`, `class_level`/`class_number`, role `member/staff/admin` นอกจากนี้ ERD ยังไม่มี `BOOK_COPIES` และ `FINE_PAYMENTS` เลยทั้งที่เป็นตารางหลักของระบบ และ `BORROW_RECORDS` ใน ERD ยังใช้ `book_id` (ของเก่าก่อนแยกเล่มลูก) แทน `book_copy_id`
**คำแนะนำ**: อัปเดต mermaid diagram ให้ตรงกับตารางรายละเอียดที่มีอยู่แล้วในเอกสารเดียวกัน (ส่วนที่ถูกต้องอยู่แล้ว ไม่ต้องแก้ใหม่ทั้งหมด)

### 14. `borrow_limit` (DB) กับ `MAX_BORROW_PER_USER` (config ฝั่งแอป) ค่าไม่ตรงกัน
Schema: `borrow_limit INT DEFAULT 5` ต่อ user แต่ละคนแก้ได้เอง / `config/app.config.ts`: `MAX_BORROW_PER_USER: 3` (ค่าคงที่ ใช้เดียวกันทุกคน) — สองค่านี้ตอบคำถามเดียวกันแต่ไม่ sync กัน และค่าเริ่มต้นไม่ตรงกันด้วย (5 vs 3)
**คำแนะนำ**: เลือกใช้แหล่งความจริงเดียว — แนะนำให้ `users.borrow_limit` เป็นตัวตัดสินใจจริงตอนเช็คสิทธิ์ยืม (เพราะปรับต่อคนได้ เช่น ครูอาจยืมได้มากกว่านักเรียน) ส่วน `MAX_BORROW_PER_USER` ใน config ให้เปลี่ยนความหมายเป็น "ค่าเริ่มต้นตอนสร้าง user ใหม่" เท่านั้น ไม่ใช่ค่าที่ใช้เช็คจริงตอนยืม (และควรปรับให้เท่ากับ 5 เพื่อไม่ให้สับสน)

### 15. Flow "เช็คเอาท์อัตโนมัติ" มีพูดถึงใน config แต่ไม่มี SQL รองรับ
`AUTO_CHECKOUT_HOUR: 17` ถูกกำหนดไว้ใน config แต่ในสคริปต์ SQL เดิมมีแค่ `mark_overdue_books()` (สำหรับหนังสือเกินกำหนด) ไม่มีฟังก์ชันคู่กันสำหรับ auto-checkout ห้องสมุด
**แก้แล้ว**: เพิ่มฟังก์ชัน `mark_auto_checkout()` พร้อมตัวอย่าง `pg_cron` schedule ที่ 17:00 ทุกวัน (คอมเมนต์ไว้ท้ายไฟล์ เปิดใช้เองตอน setup จริง)

## 🔵 คำแนะนำเสริม (ไม่ใช่บั๊ก แต่ควรพิจารณา)

### 16. เพิ่ม defense-in-depth ที่ระดับ trigger สำหรับกฎการยืม
ตอนนี้กฎ "ห้ามยืมเกิน borrow_limit", "ห้ามยืมถ้า status='suspended'", "ห้ามยืมถ้า fine_balance เกินเพดาน" ทั้งหมดพึ่งพา Logic ฝั่ง Server Action (Next.js) เท่านั้น ถ้าวันหนึ่งมีจุดอื่นที่ insert ตรงเข้า `borrow_records` (เช่น สคริปต์ import ข้อมูล หรือบั๊กใน Server Action) กฎพวกนี้จะถูกข้ามไปเลย
**แนะนำ (ไม่ได้ใส่ใน v2 เพราะเป็น business rule ที่ควรคุยรายละเอียดก่อน)**: เพิ่ม `BEFORE INSERT` trigger บน `borrow_records` เช็ค 3 เงื่อนไขนี้อีกชั้นที่ database level เป็นเซฟตี้เน็ต — บอกมาได้ถ้าต้องการให้เพิ่มจุดนี้ จะช่วยระบุเงื่อนไข/ข้อความ error ที่ต้องการให้ตรงกับ UX ที่ออกแบบไว้

### 17. `book_copies` เปิด public SELECT ทั้งตาราง รวม `price`/`note`
ตอนนี้ policy `book_copies_select_public` ให้ทุกคนเห็นทุกคอลัมน์ รวมราคาซื้อและหมายเหตุภายในของแต่ละเล่ม ซึ่งอาจไม่ใช่ข้อมูลที่ต้องการเปิดเผยสาธารณะ
**แนะนำ**: ถ้าต้องการซ่อน `price`/`note` จากสาธารณะ ให้สร้าง view เช่น `book_copies_public` (SELECT เฉพาะ `id, book_id, barcode, status, condition`) แล้วให้หน้าเว็บฝั่ง public query จาก view นี้แทนตารางจริง — ผมยังไม่ได้ทำส่วนนี้ให้เพราะไม่แน่ใจว่าราคาซื้อหนังสือเป็นข้อมูลอ่อนไหวสำหรับโรงเรียนคุณหรือไม่ บอกได้ถ้าต้องการให้เพิ่ม

### 18. ยังไม่มี index รองรับการค้นหาชื่อผู้แต่งแบบ partial match
ตอนนี้มีแค่ full-text index (`idx_books_title_gin`) บนชื่อหนังสือ ถ้าต้องการให้ค้นหา "ผู้แต่ง" แบบพิมพ์บางส่วนได้เร็วเหมือนกัน แนะนำเปิด extension `pg_trgm` แล้วเพิ่ม GIN index บน `author` (มีโค้ดตัวอย่างคอมเมนต์ไว้ในไฟล์ v2 ให้แล้ว เปิดใช้เองได้ทันทีถ้าต้องการ)

### 19. Seed ผู้ใช้ตัวอย่างยังใช้เทคนิค bypass FK
ตามข้อ 3 ด้านบน — วิธีนี้ใช้ได้เฉพาะ dev/test เท่านั้น ก่อน deploy จริงต้องลบ/ไม่รัน seed ส่วนนี้ และสร้างผู้ใช้จริงผ่าน Supabase Auth เท่านั้น (มีคำเตือนกำกับไว้ในไฟล์ v2 ชัดเจนแล้ว)
